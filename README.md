# ML-проект: Прогнозирование рейтинга кулинарных рецептов (RecipeRanker)

## Цель проекта

Создать сервис, который прогнозирует пользовательский рейтинг нового рецепта (от 0 до 5) на основе его составляющих: списка ингредиентов, сложности, времени приготовления и описания.

**Как запустить:**
*  Склонировать репозиторий: 
```linux
git clone https://github.com/Arslan203/MSU-MLOps2025.git
```
*  Установить kaggle:
```linux
pip install kaggle
```
*  Скачать датасет:
```linux
kaggle datasets download -d irkaal/foodcom-recipes-and-reviews -f recipes.csv -p data/
kaggle datasets download -d irkaal/foodcom-recipes-and-reviews -f reviews.csv -p data/
```
*  Собрать образ:
```linux
docker build -t recipe-ranker-app .
```
*  Запустить обучение:
```linux
docker run --rm -v $(pwd)/data:/app/data:ro -v $(pwd)/models:/app/models recipe-ranker-app
```
**Бизнес-цель:**

Для онлайн-платформы с рецептами (веб-сайт, приложение) такой сервис решает две задачи:
1.  **Для пользователей:** Помогает выбрать качественный, проверенный рецепт, снижая риск неудачного кулинарного опыта.
2.  **Для платформы:** Позволяет автоматически модерировать и ранжировать новый контент. Рецепты с высоким прогнозным рейтингом можно сразу выводить на главную страницу, а авторам рецептов с низким прогнозом — давать рекомендации по улучшению (например, "возможно, стоит добавить кислотности" или "рецепт слишком сложен для заявленного времени").

### Целевые метрики

#### Метрики для продакшена:
*   **Среднее время отклика сервиса:** ≤ 300 мс (для получения прогноза по одному рецепту).
*   **Доля неуспешных запросов:** ≤ 1 %.
*   **Использование ресурсов:** Сервис должен стабильно работать в рамках стандартного контейнера (например, 1 vCPU, 2 ГБ RAM) без деградации производительности при 10 RPS (requests per second).

#### Метрики качества модели:
*   **Основная метрика:** **RMSE (Root Mean Squared Error)**. Наша цель — **RMSE ≤ 0.7**.
    *   *Обоснование:* Рейтинг измеряется по 5-балльной шкале. Ошибка в 0.7 означает, что модель в среднем ошибается меньше чем на одну звезду, что является хорошим показателем для практического применения.
*   **Вспомогательная метрика:** **MAE (Mean Absolute Error)**. Цель — **MAE ≤ 0.5**.
    *   *Обоснование:* Показывает среднюю абсолютную ошибку. Значение 0.5 означает, что в среднем мы ошибаемся на ползвезды, что еще лучше для интерпретации.

## Набор данных

Для обучения будет использоваться набор данных с Kaggle: **[Food.com Recipes and Reviews](https://www.kaggle.com/datasets/shuyangli94/food-com-recipes-and-reviews)**.

Он состоит из двух основных файлов:
1.  `recipes.csv`: Содержит информацию о ~500 тыс. рецептах.
    *   **Ключевые признаки:** `id`, `name`, `minutes` (время приготовления), `tags`, `nutrition` (пищевая ценность), `n_steps` (кол-во шагов), `steps` (текст шагов), `description`, `ingredients`, `n_ingredients` (кол-во ингредиентов).
2.  `reviews.csv`: Содержит ~1.4 млн отзывов пользователей.
    *   **Ключевые признаки:** `recipe_id`, `author_id`, `rating`, `review` (текст отзыва).

**Целевая переменная (Target):**
В качестве таргета будет использоваться средний `rating` для каждого `recipe_id`, рассчитанный на основе данных из `reviews.csv`. Рецепты с малым количеством отзывов (например, меньше 5) будут отфильтрованы для повышения стабильности целевой переменной.

## План экспериментов

1.  **Исследовательский анализ данных (EDA):**
    *   Изучить распределение рейтингов. Выявить дисбаланс (например, преобладание высоких оценок).
    *   Проанализировать распределение числовых признаков (`minutes`, `n_steps`, `n_ingredients`).
    *   Исследовать текстовые данные: самые частые ингредиенты, глаголы в шагах приготовления.
    *   Провести очистку данных: обработка пропусков, удаление выбросов (например, рецепты с временем приготовления 0 минут или несколько лет).

2.  **Формирование признаков (Feature Engineering):**
    *   **Текстовые признаки:**
        *   `ingredients`, `description`, `steps`: векторизация с помощью `Tf-Idf`.
        *   Извлечение именованных сущностей (продуктов) из текста.
    *   **Числовые признаки:**
        *   `minutes`, `n_steps`, `n_ingredients`, числовые значения из `nutrition`: нормализация или стандартизация.
        *   Создание полиномиальных признаков для числовых переменных.
    *   **Категориальные признаки:**
        *   `tags`: применение `CountVectorizer` или `OneHotEncoder` для самых популярных тегов.

3.  **Выбор и обучение моделей:**
    *   **Baseline:** Создать простую baseline-модель, например, `Ridge` или `Lasso`, чтобы иметь точку отсчета.
    *   **Основные модели:** Обучить и сравнить ансамблевые модели, хорошо работающие на табличных данных:
        *   `RandomForestRegressor`
        *   `LightGBM` (или `XGBoost`)
    *   **Эксперимент с NLP:** Попробовать использовать предобученные эмбеддинги (например, `fastText`) для векторизации ингредиентов и шагов, чтобы лучше уловить семантику.

4.  **Оценка и итерации:**
    *   Проводить оценку моделей с помощью кросс-валидации (k-fold).
    *   Сравнить модели по метрикам **RMSE** и **MAE**.
    *   Проанализировать ошибки лучшей модели: на каких типах рецептов она ошибается сильнее всего?
    *   Вернуться к шагу 2 для генерации новых признаков (например, "соотношение белков к жирам", "наличие редких ингредиентов") и/или к шагу 3 для подбора гиперпараметров лучшей модели.

## Тестирование

Проект включает комплексную систему тестирования:

### Запуск тестов

```bash
# Запуск всех тестов
pytest tests/ -v

# С покрытием кода
pytest tests/ -v --cov=src --cov-report=html --cov-report=term

# В Docker контейнере (без coverage для избежания проблем с правами)
docker run --rm recipe-ranker-app python -m pytest tests/ -v

# В Docker с coverage (если нужно)
docker run --rm -e COVERAGE_FILE=/tmp/.coverage -e COVERAGE_HTML_DIR=/tmp/htmlcov recipe-ranker-app python -m pytest tests/ -v --cov=src --cov-report=term
```

### Структура тестов

Тесты покрывают следующие модули:
- `tests/test_data_loader.py` - тесты загрузки и предобработки данных
- `tests/test_data_validator.py` - тесты валидации данных
- `tests/test_predictor.py` - тесты постобработки предсказаний
- `tests/test_trainer.py` - тесты обучения модели

Всего **58 тестов**, проверяющих:
- Корректность предобработки данных
- Валидацию входных данных (формат, типы, диапазоны)
- Постобработку предсказаний для API
- Работу пайплайна обучения

### Автоматический запуск тестов

#### GitHub Actions (CI/CD)

Тесты автоматически запускаются при каждом коммите через GitHub Actions:

- **При push** в любую ветку
- **При pull request** в любую ветку
- Проверка линтера (flake8)
- Проверка форматирования (black)
- Запуск всех тестов (pytest)
- Проверка покрытия кода (coverage)

Файл конфигурации: `.github/workflows/ci.yml`

Проверить статус CI можно в разделе "Actions" на GitHub.

#### Pre-commit hooks (локальная проверка)

Для проверки перед коммитом локально можно использовать pre-commit hooks:

**Установка:**
```bash
# Установить pre-commit
pip install pre-commit

# Активировать hooks
pre-commit install
```

**Использование:**
После установки при каждом `git commit` автоматически будут выполняться:
- Форматирование кода (black)
- Проверка линтера (flake8)
- Запуск тестов (pytest)

Если проверки не пройдут, коммит будет отменен.

**Ручной запуск всех проверок:**
```bash
pre-commit run --all-files
```

**Отключение на один коммит:**
```bash
git commit --no-verify -m "сообщение"
```

**Альтернативный способ (простой bash hook):**

Если не хотите использовать pre-commit, можно установить простой bash hook:

```bash
# Скопировать hook
cp scripts/pre-commit-hook.sh .git/hooks/pre-commit
chmod +x .git/hooks/pre-commit
```

### CI/CD

Настроен автоматический запуск тестов через GitHub Actions:
- Тесты запускаются при каждом коммите в `main`, `master`, `develop`
- Проверка линтера (flake8) и форматирования кода (black)
- Проверка покрытия кода (pytest-cov)

Файлы конфигурации:
- `.github/workflows/ci.yml` - основной CI workflow
- `.pre-commit-config.yaml` - конфигурация pre-commit hooks
- `pytest.ini` - конфигурация pytest
- `.flake8` - конфигурация линтера
